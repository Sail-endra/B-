# Evaluation

`eval/RESULTS.md` holds the current numbers and is regenerated by `make eval`.
This file explains how the harness is built and what its numbers are worth.

## The question set

82 questions in `eval/benchmark/questions.jsonl`, in five slices:

| slice | n | why it exists |
|---|---|---|
| `natural` | 33 | Hand-written in student phrasing. |
| `generated` | 10 | Paraphrased from a source chunk. Vocabulary-inflated; reported for contrast. |
| `out_of_corpus` | 25 | Hand-written adversarial. Must refuse. |
| `humanities_adversarial` | 10 | Quantitative phrasing on a course with no data link. |
| `compositional` | 4 | Requires more than one tool. |

There are 48 in-corpus questions across the natural, generated, and
compositional slices. The rebuilt benchmark contains 2,183 chunks across four
courses. `eval/RESULTS.md` is the aggregate retrieval report. The Gemini
explanation sweep is separate; its local generated JSON contains per-question
text and is intentionally ignored by Git.

### The circularity problem, and the split that addresses it

The efficient way to build this set is to sample chunks and have a model write one
question per chunk — gold labels come free. But every such question is written
*by looking at its own answer*, so it inherits that chunk's vocabulary and
inflates every lexical signal. That is exactly the signal the BM25 ablation row
exists to measure, so a single blended number would overstate the gain from
fusion.

Hence the `generated` / `natural` split, reported separately, always. The
out-of-corpus questions are hand-written: models produce weak adversarial examples.

### Gold labels are page ranges, not chunk ids

```json
{"gold": [{"source": "tb_macro", "pages": [462, 462]}]}
```

Resolved to chunk ids at eval time by `dataset.resolve_gold`. Had gold been
stored as chunk ids, every change to chunk size, the parent/child split or the
equation detector would silently invalidate questions — and it would fail
*quietly*, as a mysterious recall drop rather than an error. `dataset.validate()`
runs before every eval and fails loudly if any span no longer resolves.

## Metrics

**Retrieval.** recall@{1,3,5,10}, MRR, nDCG@10. Recall is hit-rate style: several
chunks commonly express the same fact, so requiring all of them would penalise a
correct retrieval.

Recall@5 is near-saturated on a corpus this small — **recall@1 and MRR are the
columns that discriminate**, which is why finer-grained k values are reported.

**Refusal.** Precision and recall on the out-of-corpus set, both always. A system
that refuses everything scores perfect precision and is useless, so recall is what
keeps the number honest. `in-corpus answered` is reported alongside because
over-refusal is the cost that precision alone hides.

**Groundedness.** Answers decomposed into atomic claims, each checked against the
cited passages. An LLM judge when a model is configured; a lexical coverage judge
otherwise.

## Things this harness got wrong, and what changed

The harness is worth having because it caught real defects. Three, in order:

**1. The reranker was making ranking worse.** The first ablation showed r@1
dropping from 0.867 to 0.807 when reranking was enabled. But reranking could not
just be removed — RRF scores are a function of list length, not relevance, so they
cannot drive a refusal threshold. The resolution was a `confidence` mode: keep the
fused order, use the reranker only for the calibrated score. This is now the
default, and the ablation reports both modes.

**2. Refusal had a ceiling that no threshold could lift.** Out-of-corpus questions
whose *topic* was in the corpus scored as high as genuine ones. Raising the
threshold to catch them refused real questions instead. This produced
`api/retrieval/intent.py`, a separate signal composed with relevance; the
RESULTS table shows the with/without rows.

**3. The harness had a blind spot the browser found.** Compositional questions
were excluded from refusal scoring. A manual test in the UI showed the system
refusing "Does the data still support what chapter 11 claims…" while displaying
the correct passage at rank 1. Two causes: the coverage score fell as questions
got longer, and — worse — IDF on a small corpus ranks *framing* words ("still",
"claims", "data", "support") above topic words ("unemployment", "inflation"),
because a textbook rarely says "still". Fixed by dropping framing vocabulary
before ranking terms by IDF, and compositional questions are now scored.

The numbers went *down* when the third fix landed, because the harness began
measuring cases it had been skipping. That is the correct direction for an honest
harness.

## What the current numbers are not

- **Not a measurement of the production stack.** The committed run uses local
  TF-IDF+SVD embeddings, a lexical reranker, an extractive answerer, and synthetic
  FRED data. Every report states this at the top.
- **Not a universal corpus-scale result.** The benchmark has 2,183 chunks, but
  results characterize only these four courses and labels.
- **Groundedness of 1.000 is a tautology offline.** The extractive answerer quotes
  retrieved sentences verbatim, so it *cannot* emit an ungrounded claim. The report
  says so in bold. This metric only becomes meaningful with a generative model.
- **The refusal threshold is not portable.** It is calibrated against this corpus
  and this reranker. Re-run `make calibrate` after any retrieval change.

## Running

```bash
make eval          # everything, writes eval/RESULTS.md
make eval-fast     # retrieval + refusal only
make eval-ablate   # the ablation table
make calibrate     # sweep the refusal threshold
make baseline      # bare-model comparison (needs ANTHROPIC_API_KEY)

make eval OFFLINE=0   # any target, against configured keys
```

The retrieval suite defaults to offline mode. The explanation groundedness sweep
is intentionally online: it uses the configured Gemini model for both generating
the explanation and judging its claims. Keep it on the benchmark corpus only; it
is not a product-data evaluation. It runs 48 in-corpus questions at both
`concise` and `in_depth`, records answers/refusals, claim counts, judge fallbacks,
and groundedness rates, and writes detailed output to the ignored JSON path:

```bash
COPILOT_OFFLINE=0 ./.venv/bin/python -m eval.run_explanation_grounding \
  --json eval/explanation_grounding.json
```

Set `GEMINI_API_KEY` in `.env` and ensure `COPILOT_OFFLINE=0`; the script reports
the active backend and fails if no generative model is available. Do not publish
the detailed per-question output by default.
